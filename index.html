從後端工程師到 AI 工程師的橋接手冊

這不是一份「從頭學 AI」的教材，而是一份針對你的背景量身裁切的知識補完計畫： 目的是讓你在面試桌上，不只能說出「我做過 Threat Intel Agent」， 還能把它背後每一個技術選擇的原理講清楚——為什麼是 Prompt Engineering 而不是微調、 Attention 到底在算什麼、你的 TQC+ 機器學習證照背後的演算法實際上做了什麼決策。

Step 0 · 效率的起點

先算清楚：什麼不用教，什麼才是真缺口

效率的第一步不是「教得快」，是「不教你已經會的」。這份框架先把你履歷裡已經驗證過的能力 劃出來——省下的每一小時，都留給右邊那欄。

已經會・這份文件不重教
  • Python 與非同步架構：FastAPI + Uvicorn、Flask、Decorator、路由設計
  • 資料庫實戰：MySQL 交易設計、Redis 高併發鎖（SET NX）、MongoDB／Firebase NoSQL 建模
  • 系統落地：Docker 容器化、Git 協作、Railway／Heroku／Render 部署
  • LLM 應用層：Anthropic Tool Use 兩輪架構、tool_choice 強制結構化輸出、多外部 API 整合
  • ML 操作層：TQC+ 機器學習證照代表你會「呼叫」sklearn——這份文件不重講怎麼呼叫
真缺口・這份文件要補的
  • 傳統 ML 為什麼 work：決策樹怎麼選分裂點、集成學習為何比單一模型準
  • DL 的訓練機制：Autograd／反向傳播／為什麼要梯度下降而非解方程式
  • Transformer 內部：你只會「呼叫」Claude，還不懂 Attention 在裡面算什麼
  • 對齊三部曲：SFT／RLHF／DPO 的差異，以及 Prompt／RAG／微調／自訓模型怎麼取捨
  • 把理論講回自己專案：面試最常問「你的專案為什麼這樣設計」，現在缺的是這條連線

設計依據

六個核心策略，對應你說的學習特質

每一條策略都直接回應你提到的學習方式，不是通用的教學法模板。其中 05、06 是根據你的補充修正過的版本——順序比類比更重要。

01 — 對應「喜歡具體、離散」

先給步驟表，不先給連續公式

每個機制都先拆成一張「第1步做什麼、第2步做什麼」的離散表格，數字帶入實際跑一次；連續的數學推導放在最後，當作「想更深挖再看」的選讀。

02 — 對應「用簡單應用解釋深問題」

一個案例貫穿到底，但案例晚一點才出現

全程只用一個問題：「這個 IP／這篇留言是不是威脅？」直接延伸你 Threat Intel Agent 的真實資料。但案例只在地基蓋好、元件疊完之後才代入——案例是拿來驗證你懂了，不是拿來替代理解。

03 — 對應「專有名詞記憶弱」

後端工程師翻譯詞典

新名詞第一次出現就配一句你熟悉的系統類比（Attention ≈ 加權版 SQL JOIN），之後全文重複用同一個類比，不重新定義。但類比放在機制講完「之後」，當記憶的鉤子，不是理解的捷徑。

04 — 對應「面試 + 工作，要懂不只要會做」

每個模組收尾都是一題面試模擬

不會停在「這個技術是什麼」，而是逼近「面試官問你為什麼這樣做，你答不答得出設計依据」，草稿直接連回你的三個真實專案，讓你有話術也有底氣。

05 — 對應「要從最基礎的底層概念開始」

先蓋地基，再一層層往上疊

每個機制都先講一個跟任何案例、任何應用都無關的最原始概念（例如 Attention 之前，先搞懂「兩個向量的相似度」是什麼），再一步一步疊加元件到完整機制。地基不蓋好，案例跟類比都只是背下來的表演。

06 — 對應「表格／流程圖／心智圖／架構圖」

依內容性質挑對的視覺呈現，不是每次都套同一種

有嚴格先後順序的機制用流程圖；互相比較、彼此獨立的選項用表格；元件之間互相關聯但沒有固定順序的全貌用心智圖；系統組件與資料流用架構圖。下面模組總覽表後面有一張對照表說明怎麼選。

持續累積

後端工程師翻譯詞典（節錄）

正式產出各模組內容時，每個新名詞都會加進這本詞典，最終會附在文件最前面當速查表—— 這是專門針對你「專有名詞記憶弱」設計的外部記憶，不需要背，需要查。

梯度下降Gradient Descent

不是解方程式直接求出答案，是像二分搜尋一樣每次朝誤差變小的方向挪一小步，挪到誤差不再明顯下降為止。

過擬合Overfitting

模型把訓練資料的雜訊背下來，就像寫死一堆 if/else 硬 hardcode 每一筆測試資料，換一批新資料就全部失準。

微調Fine-tuning

不是重寫整個系統，是對一個已經上線的服務做 config override——用少量新資料，在既有權重基礎上小幅調整。

人類反饋強化學習RLHF

像是先訓練一支自動化 Code Review 機器人（Reward Model）學會人類的偏好排序，再讓它去打分數，取代真人一筆一筆審查。

檢索增強生成RAG

跟你在 API 裡先 query DB 拿資料再組 response 是同一套邏輯——先檢索正確資料，再交給模型生成回答，而不是純靠模型記憶亂猜。

批次量／訓練週期Batch Size / Epoch

Batch Size 像分頁查詢的 page size，Epoch 像對整張表跑完一次 for 迴圈——訓練就是重複跑很多個 Epoch。

收尾設計

為什麼每個模組都要接一題面試模擬

你說目標是面試跟工作，不只是學會操作。這份框架把「懂」直接定義成 「講得出設計依据、答得出取捨」，而不是「跑得出程式碼」。舉一個 M7 的例子：

Q：為什麼你的 Threat Intel Agent 不直接微調一個 LLM 來做資安分類，而是用 Prompt + Tool Use？

A（草稿）：「微調需要標註資料、GPU 資源跟版本維運成本，而我的情資來源是即時查詢、判斷規則也常在變，Prompt Engineering 加 Tool Use 能用很低的成本快速迭代。如果之後判斷邏輯穩定下來、資料量也夠大，可能會考慮用微調或訓練一個小型分類器（回到 M1、M2 的做法）取代持續調 Prompt——這就是 Prompt Engineering、RAG、微調、自訓模型這四種應用方式的取捨依据，不是哪個絕對比較好，是看資料量、成本跟需求穩定度。」

這類問答會在每個必修模組收尾累積成一份「面試問答草稿庫」，最後彙整成 M9 的附錄， 面試前只需要重看這一份，不用重翻九個模組。
