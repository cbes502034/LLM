AI橋接手冊 · 模組 M9 · 面試熱度 ★★★★★

專案還原室——用 M1～M8 解釋 Threat Intel Agent

前面八個模組學的是「技術本身」；這個模組反過來，逐一對照你已經做完的 Threat Intel Agent 裡每一個技術決策，回答「為什麼這樣設計」。面試官問「你這個專案為什麼這樣做」，答案都在這一頁。

01　為什麼這個模組長得不一樣

M1～M8 都是「先學一個新技術」。M9 不教新東西，是把學過的東西倒著用——你已經做完 Threat Intel Agent 了，這個模組要做的是幫你把「當初憑直覺／憑經驗做的決定」翻譯成「有理論根據的設計依据」。面試最常見的追問方式不是「你會不會 Attention」，而是「你的專案為什麼不這樣做、而是那樣做」——這個模組直接準備好那些答案。

02　專案架構總覽

先看整體：使用者輸入一個 IP 或網域，經過哪些元件，最後變成一份風險報告。

03　技術決策逐一還原——每個決定，連回一個模組

下面這張表，把你當初做的技術選擇，一項項對照回前面學過的理論。這是這個模組真正的核心。

技術決策為什麼這樣做（設計依据）對應理論
用 Prompt Engineering + Tool Use，不微調專屬分類模型情資判斷規則常變、資料量也不到需要微調的規模；微調要標註資料、要 GPU、要版本維運，Prompt 能用低成本快速迭代M7 應用四法取捨
Tool Use 兩輪架構（第一輪自由選、第二輪 tool_choice 強制）LLM 本質是機率預測（M7 底層概念），不強制的話模型會用自然語言隨意回覆、格式不穩定；強制後等於把輸出空間收斂成單一路徑，這正是「早期用 prompt 要求格式但頻繁解析失敗」問題的根因M7 語言模型本質
用 MongoDB 存情資，不是丟進傳統 ML 分類器各情資來源回傳的欄位高度不固定，不像 M1／M2 那種有固定欄位的結構化特徵；這是「非結構化文字」該用 LLM、而不是傳統分類器的典型場景M1／M2 結構化 vs M6／M7 非結構化
高風險 IP 自動寫入黑名單本質上就是一個二元分類器在某個風險分數 threshold 上做判斷；threshold 設太低＝Recall 高但 Precision 低，容易誤判正常 IP，這是 M1 教的 Precision/Recall 取捨在真實系統裡的樣子M1 混淆矩陣／threshold
判斷與執行權責分離（只寫黑名單，不主動封鎖）呼應對齊三標準裡的 Harmlessness：如果誤判就直接封鎖，等同一個沒有 KL 散度懲罰的暴走 policy，可能對正常服務造成傷害；現在的設計等於讓「人類／外部系統」保留最終否決權M7 RLHF 對齊精神
直接呼叫 Anthropic SDK，不用 LangChain確保決策過程完全透明可控、能完整記錄 Agent 每一步軌跡——這是 M1 講的「可詮釋性」評估面向，落地成一個真實系統的設計選擇M1 可詮釋性
24 小時 TTL 快取 + 兩層裝飾器純工程優化，但取捨邏輯可以類比 M8：多快取＝Exploit（相信已知結果，省成本）、多重新查詢＝Explore（冒風險換取最新資料），你選了「大部分時間 Exploit、24 小時強制過期再 Explore」的折衷M8 Exploration／Exploitation（類比，非硬理論）
04　跟業界產品對照——你的做法站在哪裡

面試官有時會問「這跟市面上的工具有什麼不同」。這張表讓你先想過一次：

產品／方案做法跟你的 Threat Intel Agent 比較
VirusTotal 網頁版單一資料源查詢 + 規則式聚合，不做跨來源的自主推理你的系統多做了一層「Agent 自主判斷該查哪些來源、怎麼交叉比對」，VirusTotal 本身只是你系統裡的一個資料源
傳統 SIEM 規則引擎（如 Splunk 規則告警）人工寫死 if/then 規則，規則不會因為新型態攻擊自動調整你的系統用 LLM 理解非結構化文字（如 Abuse Report 全文），規則式引擎做不到這件事（M6／M7 的核心價值）
企業級商用 Threat Intelligence Platform（如 Recorded Future）通常是自建的大規模資料管線 + 專屬訓練模型，成本極高你的系統用「呼叫已對齊好的 LLM + Prompt Engineering」達到類似效果，成本低很多，但目前準確度與規模仍不能直接相比——這正是 M7 應用四法裡「自己訓練模型」那一格的取捨
05　面試問答總彙——專案層級的追問

前面每個模組都有一題「概念層級」的面試模擬（例如 M6 的「你了解 Attention 嗎」）。這裡收的是「專案層級」的追問，通常緊接在概念題後面：

Q：為什麼你的 Threat Intel Agent 選擇 LLM Agent 架構，而不是傳統的規則引擎或機器學習分類器？

A（草稿）：「情資分析的輸入是高度非結構化的——WHOIS 回傳的欄位、Abuse Report 的文字內容，每個來源格式都不一樣，規則引擎會需要窮舉所有格式變化，維護成本很高；傳統 ML 分類器則需要先做特徵工程，把這些非結構化資料轉成固定欄位，但情資來源的結構本身就一直在變。LLM 的優勢正是能直接理解非結構化文字、還能自主判斷該查哪些來源，這是 M1／M2 那種結構化分類器做不到的。」

Q：如果要提升這個系統的準確度，你會怎麼做？

A（草稿）：「短期會先看 Prompt 能不能調得更精準，成本最低；如果之後累積了足夠多『已標註』的判斷結果（哪些 IP 事後證實真的是威脅），我會考慮先用 M1／M2 的方法（例如 Random Forest）做一個輕量的本地初篩分類器，過濾掉明顯安全或明顯危險的案例，只把邊界案例送給 LLM 做更細緻的判斷——這樣能同時省 API 成本、也提升整體準確度。真的要走到微調或自訓模型，要等資料量跟穩定度都到一定門檻，這就是 M7 那張應用四法取捨表在講的事。」

Q：你怎麼確保 LLM Agent 不會亂查、浪費 API 額度，或做出錯誤決策？

A（草稿）：「三層設計：第一，兩輪 Tool Use 架構把『決策自由度』限制在第一輪，第二輪強制輸出格式，避免它自由發揮；第二，24 小時 TTL 快取加裝飾器封裝，避免重複查詢同一個目標浪費額度；第三，完整記錄每一步決策軌跡到獨立資料表，就算真的判斷錯誤，也能回溯是在哪個環節出問題，而不是只有一個黑盒結論。」

Q：這個系統要怎麼往「AI 工程師」更核心的技能演進？

A（草稿）：「目前這個專案完全是應用層——呼叫別人預訓練、對齊好的 Claude。下一步我想做的是：先用 M1／M2 學到的方法，拿系統累積的決策軌跡跟人工回饋訓練一個本地輕量分類器；再研究 M7 提到的 LoRA 類輕量微調技術，看能不能微調一個開源模型專門處理資安文本分類，補齊我目前『只會呼叫、不會訓練』的缺口。」
