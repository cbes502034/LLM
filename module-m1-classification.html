分類判官——用一個閾值決定機器怎麼判你有罪

你的 Threat Intel Agent 最後一定要做出一個二元判斷：這個 IP 要不要寫進黑名單。這個模組要讓你不只會呼叫 .score()，還能在面試上解釋為什麼有時候該選 Precision、有時候該選 Recall，以及閾值到底是怎麼設出來的。

01　為什麼要學這個

面試官幾乎必問「你怎麼評估一個分類模型好不好」，如果只回答「看 accuracy 高不高」，很容易被追問到答不出來。你的 Threat Intel Agent 裡「風險分數超過某個門檻就判定為威脅」這個動作，其實就是一個分類器在某個 threshold 上做決策——這個模組把這句話拆成完整、能在面試上站得住腳的評估語言。

02　底層概念（完全不談案例，只談最原始的東西）

先把「猜對猜錯」這件事本身拆開來看。假設有一個粗略的判斷器，要對 20 個樣本各做一次「是否符合某條件」的猜測，猜完之後跟真實答案對一下，猜對猜錯其實不是只有「對／錯」兩種結果，而是可以拆成四種組合：

實際為「是」實際為「否」
判斷為「是」TP 真陽性 = 8FP 偽陽性 = 3
判斷為「否」FN 偽陰性 = 2TN 真陰性 = 7

四個象限的意思：TP＝猜「是」而且真的是；FP＝猜「是」但其實不是（誤判）；FN＝猜「否」但其實是（漏判）；TN＝猜「否」而且真的不是。這張 2×2 表格就是整個模組的地基，完全還沒牽扯到任何分類問題的實際場景，純粹是「猜測 vs 事實」的四種組合。

03　逐層往上疊——從流程到公式

地基蓋好之後，一步一步加元件。首先是監督式學習最基本的三段流程：

「測試樣本」從哪裡切出來，有三種常見做法：

切分方法做法適合情境
訓練測試法一次切分，常見 75/25 比例樣本數大，切一次就有代表性
k 疊交互驗證法
k-fold cross-validation		資料切成 k 份，輪流當測試集，其餘當訓練集樣本數中等，想更穩定地估計效能
自助法
bootstrap		取後放回抽樣，重複產生訓練集樣本數極小，經不起切一刀

模型好不好，光看「準不準」也不夠，面試官期待你從五個面向去講：準確度（猜對的比例）、速度（訓練/預測要多久）、可詮釋性（能不能講出為什麼這樣判）、健全性（面對雜訊或缺值容不容易失準）、擴展性（資料變大能不能撐得住）。

接著把 02 步驟的四象限疊成公式。還是用同一組抽象數字（TP=8, FP=3, FN=2, TN=7，共 20 筆）：

指標公式白話意義代入計算
Accuracy 準確度(TP+TN)/All全部猜對的比例(8+7)/20 = 0.75
Precision 精確率TP/(TP+FP)你猜「是」的裡面，猜對幾成8/(8+3) ≈ 0.73
Recall 召回率TP/(TP+FN)所有真正「是」的裡面，你抓到幾成8/(8+2) = 0.80
F1-Score2·P·R/(P+R)Precision 與 Recall 的調和平均2(.73×.80)/(.73+.80) ≈ 0.76

再往上疊一層：如果把「判斷為是」的門檻（threshold）從高調到低，這組 TP/FP/FN/TN 會整組跟著變，也就會產生一整串不同的 Precision/Recall 組合。把這串組合畫成「橫軸 FPR（偽陽性率）、縱軸 TPR（真陽性率）」的曲線，就是 ROC 曲線；曲線下面積叫 AUC，用來衡量「不管門檻設在哪，這個模型整體有多好」。

04　現在才代入具體案例

地基跟公式都蓋好了，這時候才套進「這個 IP 是不是威脅」的貫穿案例。假設你的 Threat Intel Agent 對 10 個 IP 做威脅判斷，其中 7 個真的是威脅、3 個是安全的，模型判斷結果如下：

實際為威脅（7個）實際為安全（3個）
判斷為威脅TP = 6FP = 2
判斷為安全FN = 1TN = 1
Accuracy = (6+1)/10 = 0.70 Precision = 6/(6+2) = 0.75 ← 判定為威脅的8個裡，6個真的是 Recall = 6/(6+1) ≈ 0.86 ← 7個真威脅裡，抓到了6個 F1-Score = 2×.75×.86/(.75+.86) ≈ 0.80

如果把判定門檻（threshold）調低，會有更多 IP 被歸類成「威脅」，FN 會變少、Recall 會上升，但同時 FP 也會變多、Precision 會下降——這就是 07 步驟裡黑名單機制那個真實的取捨。

05　類比鎖記憶——用 API／SQL 掛住指標

機制都懂了之後，才用你熟悉的後端類比把它釘進長期記憶：

混淆矩陣 ≈ 一張「預測結果 vs 正確答案」的交叉對帳表（pivot table） Precision ≈ API回傳結果的「精準度」：你的API吐回8筆，裡面真正是使用者要的有幾筆（訊噪比） Recall ≈ API的「覆蓋率」：資料庫裡真正符合條件的7筆，你的查詢撈出了幾筆（有沒有漏抓） Threshold ≈ WHERE risk_score > X 這行SQL裡的X，X越低撈出越多（Recall高）但雜訊也越多（Precision低） AUC ≈ 不看單一次查詢，而是看這支API在「所有可能的X」下平均表現多好

Precision 跟 Recall 永遠是一組互相拉扯的關係，就像你不能同時把 API 的「準」跟「全」都調到最高——這正是 09 步驟面試題要你講清楚的取捨。

07　業界實際應用案例

不是只有你的 Threat Intel Agent 在用這套邏輯，面試被問「這個技術有什麼應用」時要答得出真實產品：

應用領域具體場景為什麼看重的指標不一樣
垃圾郵件過濾Gmail 垃圾信分類誤判正常信＝FP，會讓使用者漏看重要郵件，所以 Precision 比 Recall 更被看重。
醫療篩檢癌症篩檢初篩漏掉真陽性＝FN，後果是延誤治療，所以 Recall 比 Precision 更被看重，寧可多做一次複檢。
金融詐騙偵測信用卡即時攔截同樣偏向 Recall 優先，但 FP 太多會炸掉客服量，需要在兩者間找一個可營運的平衡點。
你的 Threat Intel Agent高風險 IP 自動寫入黑名單這其實就是一個分類器在某個 threshold 上做判斷：threshold 設太低＝Recall 高但 Precision 低，容易誤擋正常 IP，這是你在設計時要跟面試官講清楚的取捨。
08　名詞卡（後端翻譯詞典）
混淆矩陣Confusion Matrix

一張「預測結果 vs 正確答案」的交叉對帳表，四個象限就像資料庫查詢結果跟正解逐筆對帳後的四種結果。

精確率Precision

API 回傳結果的精準度：吐回的資料裡，真正是使用者要的有幾筆（訊噪比）。

召回率Recall

API 的覆蓋率：資料庫裡本來就符合條件的資料，你的查詢撈出了幾筆，有沒有漏抓。

F1 分數F1-Score

幫 Precision 跟 Recall 做負載平衡的綜合分數，其中一個掉太低，F1 就會被拉低，不能用另一個高分護航。

ROC 曲線ROC Curve

把 WHERE score > X 裡的 X 從 0 掃到 1 畫出來的召回率／誤判率曲線，X 就是可調的 threshold 參數。

曲線下面積AUC

幫整條 ROC 曲線打一個總分，用來比較「不看單一 threshold、看整體品質」時哪個模型比較好，像是跨參數組合的平均表現。

09　面試模擬

Q：如果你的分類模型 Recall 很高、但 Precision 偏低，這代表什麼？你會怎麼處理？

A（草稿）：「代表模型抓到了大部分真正的正樣本，但同時誤判了不少負樣本。以我做的 Threat Intel Agent 為例，如果把判定威脅的 threshold 調低，會有更多 IP 被標記成威脅，這時候像案例裡 TP=6、FP=2 那組數字，FP 就會繼續往上跑，Recall 提高但 Precision 下降。要怎麼處理要看下游代價：如果誤判的後果只是多發一次告警給人工複查，影響不大；但如果是自動把 IP 寫進防火牆黑名單、會直接擋掉正常流量，那我會傾向拉高 threshold、犧牲一點 Recall 換 Precision，或是在自動化流程前面加一層人工複核，而不是讓分類器直接落地執行高風險動作。」

10　效率檢查點

合上這頁，只憑 02 步驟那張 2×2 表格（TP/FP/FN/TN），把 Precision、Recall、F1 的公式跟白話意思重新推一次，再用 04 步驟的 10 個 IP 案例（TP=6, FP=2, FN=1, TN=1）親手算一次三個指標。算得出來、講得出白話意思，才算真的疊上去了。
